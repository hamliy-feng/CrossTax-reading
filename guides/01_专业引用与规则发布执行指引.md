# 专业引用与规则发布执行指引

执行对象是具体交易的法源与适用规则。产出研究资料和入库提案；现有正式发布条件不因模型检查而改变。

## 先建立任务

工作目录 `research/rule_packages/<packet_id>/`。使用付款方、收款方、所得及日期定义场景，例如 `CN-SG-EQUIPMENT-20261007`。先填写 `scope.json`：法域方向、主体类型、交易日期、合同权利、金额币种、税种、目标问题、缺失事实。金额和比例用十进制字符串。

不把对新加坡支付与新加坡对外支付混为一个场景。不以合同标题代替所得分类，不用协定税率推断国内法一定征税。

## 资料整理

从税务机关、立法机关、法院及协定双方网站开始；事务所资料只作为寻找文书的线索。

1. 查官方目录，找到具体协定、议定书、换文、国内法律、行政规则、法院判决和程序文件。
2. 保存原始 HTTP 内容或 PDF；记录请求 URL、最终 URL、HTTP 状态、获取 UTC 时间、内容类型、字节数和 SHA-256。沿用 `data/raw/<jurisdiction>/` 的既有原件索引；新原件使用 SHA 命名，不可覆盖旧原件。
3. 把官方来源和实际文件登记到 `sources`、`documents`、`document_versions` 的 SQL 提案；每条引文记录原始文献版本。
4. 无法获取时记录错误原因与官方入口，不把发现链接写成已下载。扫描 PDF 无可读文字时记录需文字识别，不伪造页码内容。

## 交叉检查

默认进行三次独立 DeepSeek 请求：A 整理原文，B 检查 A 与原文，C 只处理 A/B 冲突。每次提供同一输入快照和定位，不把 A 的结论作为 B 的唯一依据。模型输出与原文同时保存；程序复算字节 SHA 和引用定位。

核查表至少含以下项目：

| 项目 | 检查依据 | 不足时处理 |
|---|---|---|
| 文书身份 | 正式标题、双方、语言、文书类型和签名页 | 留空或标记争议 |
| 签署、生效、适用 | 三种日期分别引用；按税种和缔约方区分适用时点 | 禁止从签署日推断生效 |
| 后续版本 | 所有议定书、换文、替代文本与废止范围 | 不能只查最新 PDF |
| MLI | 双方覆盖协定清单、保留/通知、匹配条款及按税种适用时间 | 综合文本作为辅助，保留法律文书链 |
| 双方国内法 | 来源规则、主体、税基、豁免、征管与税期 | 协定上限不直接等于实际税额 |
| 交易条件 | 居民、受益所有人、持股、常设机构、PPT、合同权利 | unknown 与 false 分开 |
| 程序 | 居民证明、申请/申报、备案、扣缴责任、截止日期 | 单列待补材料，不虚构办税动作 |

每项结论记录 `claim_id`、原文摘录、条号、PDF 物理页码或 HTML 段落、URL、版本 ID、原件 SHA、条文 SHA、适用事实、适用时点、例外、冲突来源。原件扫描页与印刷页分开记录。

## 结构化规则包

`rule_packet.json` 使用以下结构；示例中的 null 需要从原文产生，不能直接补猜测值：

```json
{
  "packet_id": "CN-SG-EQUIPMENT-20261007",
  "payer": "CN", "recipient": "SG", "income_type": "ROYALTIES",
  "transaction_subtype": "industrial_commercial_scientific_equipment",
  "tax_type": null, "taxpayer_type": null,
  "effective_from": null, "effective_until": null,
  "tax_base": null, "nominal_rate": null, "taxable_fraction": null,
  "required_facts": [], "exceptions": [], "procedure": [],
  "evidence": [], "disputes": [], "missing_evidence": [],
  "checks": {"version_complete": false, "both_domestic_laws_complete": false},
  "status": "research_candidate"
}
```

规则同时交付可读说明：为什么适用/不适用、何时切换到另一条款、哪些材料会改变结论。不要把模型评分写成法律正确概率。

## 争议处理

先定位争议是事实、翻译、版本、法源效力还是计算。C 请求只比较双方引文与当前事实。解决时引用决定性原文；无法解决时保留双向证据和最小补充资料。不得凭多数模型意见把 unknown 改成 true。程序检查无法证明法律效力时，只能记录程序检查通过。

## 入库与现有发布闸门

交付 `proposed.sql`，只含专属 `crosstax` schema 的事务化增量提案。维护者先 `BEGIN`、验证目标库和原件，检查外键/冲突/历史版本，再执行与验收；失败回滚。禁止修改其他项目实例。

现有迁移 `030` 区分 L1 原文候选、L2 引用及 L3 规则。L2 需要官方文书身份、真实条文边界和对应条文 SHA 的法律审核记录，L3 还需带时点、条件的明确规则。模型提取不能自行把 `boundary_status` 改成 `expert_verified` 或把状态改成 `professionally_reviewed`。

迁移 `031/032` 的统一正式发布视图需要：全部官方原件有 SHA；协定修改、双方 MLI、国内法、税种税期及扣缴程序检查齐全；没有开放高/严重阻断项；实际对应审核记录精确匹配包与证据 SHA；通过的案例与方向、所得、子类、日期和事实一致。`qa_reviews` 的真实审核人及签字不能由模型虚构。

本次课程作业采用模型独立检查和程序验收，输出可作为研究候选、案例演示与条件算例。没有真实条件支撑的专业字段保持原状态，正式发布视图仍返回 0 也应如实记录。可以完整交付研究材料，不能用假身份绕过闸门。

## 必须产出的文件

- `scope.json`：场景和事实。
- `sources.jsonl`：原件 URL、时间、字节 SHA 和路径。
- `review.md`：逐项核查表、条款引用、版本链及结论。
- `rule_packet.json`：结构化规则、条件、例外和缺口。
- `disputes.md`：冲突及裁决/未解决原因。
- `proposed.sql`：可回滚的增量入库提案。
- `runs/`：实际模型、输入/输出 SHA、响应状态；不保存 Key。
- `acceptance.json`：SHA 重算、定位一致性、日期/分类/条件反例、实际规则视图命中。

验收通过应精确说“资料结构/程序检查通过”或“指定场景满足正式发布条件”；不得以 PDF 数、模型答复或 JSON 字段齐全代替法律适用验收。

AI 可能会说错，请注意甄别。
